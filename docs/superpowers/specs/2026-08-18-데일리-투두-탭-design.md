# 데일리 투두 탭 — 설계

- 날짜: 2026-08-18
- 대상: 배추가족 PWA (`baechoo-family`)
- 배경: 하단 `🗓️ 캘린더` 탭의 첫 서브탭인 가족 캘린더를 쓰지 않게 됐다. 그 자리를 매일 체크하는 데일리 투두로 바꾼다.

## 1. 목표

부부가 함께 보는 하나의 데일리 체크리스트. 항목은 카테고리로 묶이고, 매일 갱신되며, 그날 몇 %를 했는지가 미션으로 보인다. 지난 날짜의 달성 기록은 언제든 되짚을 수 있다.

## 2. 범위

**포함**
- 가족 캘린더(서브탭·컴포넌트·타입·순수함수·테이블) 완전 제거
- 데일리 투두 신설 — 항목 CRUD, 카테고리 CRUD, 날짜별 체크, 진행률·목표·스트릭, 월간 히트맵
- 특정일 1회성 투두
- 탭 라벨·라우트 정리

**제외**
- 52주 투두, 추추 회사 캘린더는 코드 변경 없음 (서브탭 순서만 바뀜)
- 담당자(추추/배찌) 축 — 두지 않는다. 사람별로 나누고 싶으면 카테고리 이름으로 해결
- 요일 지정 반복 — 매일 아니면 특정일 1회, 둘뿐
- 알림·푸시

## 3. 탭 구조

`app/todo/page.tsx`가 서브탭 3개를 스위칭한다.

| 순서 | 라벨 | 컴포넌트 |
|---|---|---|
| 1 | 데일리 투두 | `components/dailytodo/DailyTodoApp.tsx` (신규, 기본 서브탭) |
| 2 | 52주 투두 | `Todo52App embedded` (그대로) |
| 3 | 추추 회사 | `CompanyCalendar` (그대로) |

- 하단 탭: `🗓️ 캘린더` → `✅ 투두`, href `/calendar` → `/todo`
- `app/calendar/page.tsx`, `app/todo52/page.tsx`는 `/todo`로 redirect
- 헤더 타이틀 `캘린더` → `투두`, 이모지 `🗓️` → `✅`

## 4. 데이터 모델

### 4.1 타입 (`lib/types.ts`)

```ts
/* ───────────── 데일리 투두 ───────────── */

// 카테고리 — 사용자 관리(이름 + 색). 항목을 묶고 정렬 순서를 준다.
export interface DailyTodoCategory {
  id: string;
  name: string;
  color: string;    // hex
  sortOrder: number;
  createdAt: string; // YYYY-MM-DD
}

// 데일리 투두 항목.
//   onceDate = null  → 매일 반복. startDate부터 endDate 전날까지 활성
//   onceDate != null → 그 하루만 활성 (특별 이벤트)
export interface DailyTodo {
  id: string;
  title: string;
  categoryId: string;
  startDate: string;        // 활성 시작일 (YYYY-MM-DD)
  endDate: string | null;   // 이 날짜부터 비활성(=삭제일). null = 계속
  onceDate: string | null;  // 1회성 지정일
  doneDates: string[];      // 체크한 날짜들 (YYYY-MM-DD, 오름차순 유지)
  sortOrder: number;
  createdAt: string;
}

// 미션 목표 — 단일 행
export interface DailyTodoSettings {
  goalPct: number; // 0~100, 기본 80
}
```

`DailyTodoSettings`에는 `id`를 두지 않는다. `daily_todo_settings` 테이블은 `id = 'singleton'` 한 행뿐이고, 그 id는 `repo.ts`의 매핑 함수(`toDailyTodoSettings` / `fromDailyTodoSettings`)가 붙였다 뗀다. 앱 코드가 다룰 값은 `goalPct` 하나다.

`DataSnapshot`에 `dailyTodos: DailyTodo[]`, `dailyTodoCategories: DailyTodoCategory[]`, `dailyTodoSettings: DailyTodoSettings` 추가.

### 4.2 활성 기간이 핵심인 이유

항목을 오늘 추가하면 `startDate = 오늘`, 삭제하면 `endDate = 오늘`이 찍힌다. 둘 다 **오늘부터** 효력이 생기고 어제 이전은 손대지 않는다.

이게 없으면 오늘 항목 하나를 추가할 때마다 지난달 모든 날짜의 분모가 커져 히트맵이 통째로 내려앉는다. 반대로 항목을 지우면 과거 달성률이 부풀어 오른다. 기록으로서 신뢰할 수 없게 된다.

부수 효과로 오입력이 자연히 처리된다 — 오늘 만들고 오늘 지우면 `startDate == endDate`라 어느 날짜에도 뜨지 않는다.

### 4.3 체크 기록은 `doneDates[]`

배추 건강 탭 `baechoo_health_todos.done_dates` 패턴을 그대로 쓴다. 별도 체크 테이블을 두면 행이 연 5천 개 단위로 불어나 `loadAll`이 매번 그걸 전부 끌어온다. 항목 15개 × 365일이라도 문자열 배열은 연 60KB 수준이다.

### 4.4 마이그레이션 `0027_daily_todos.sql`

현재 최신은 `0026_budget_sort_order.sql`.

**한 파일 안에 두 조각으로 나눠 쓰고, 적용도 두 번에 나눠 한다.** 아래 5절 배포 순서 참조.

```sql
-- 0027 (A) 생성 — 가산적. 코드 배포 전에 적용해도 무해하다.
create table if not exists daily_todo_categories (
  id text primary key,
  name text not null,
  color text not null,
  sort_order integer not null default 0,
  created_at date
);

create table if not exists daily_todos (
  id text primary key,
  title text not null,
  category_id text not null,
  start_date date not null,
  end_date date,
  once_date date,
  done_dates jsonb not null default '[]'::jsonb,
  sort_order integer not null default 0,
  created_at date
);

create table if not exists daily_todo_settings (
  id text primary key,
  goal_pct integer not null default 80
);

alter table daily_todo_categories enable row level security;
alter table daily_todos enable row level security;
alter table daily_todo_settings enable row level security;
drop policy if exists family_all on daily_todo_categories;
create policy family_all on daily_todo_categories for all using (true) with check (true);
drop policy if exists family_all on daily_todos;
create policy family_all on daily_todos for all using (true) with check (true);
drop policy if exists family_all on daily_todo_settings;
create policy family_all on daily_todo_settings for all using (true) with check (true);

create index if not exists idx_daily_todos_active on daily_todos (start_date, end_date);
create index if not exists idx_daily_todos_once on daily_todos (once_date);
create index if not exists idx_daily_todo_categories_sort on daily_todo_categories (sort_order);

-- 0027 (B) 제거 — 되돌릴 수 없다. 신코드 배포·동작 확인 후에만 실행한다.
-- drop table if exists family_events;
-- drop table if exists event_categories;
```

한글 시드는 SQL에 넣지 않는다(인코딩 손상 회피, 기존 규칙). `loadAll` 부트스트랩이 0행일 때만 주입한다 — `event_categories` 패턴 그대로.

기본 카테고리 시드는 `일상` 1개. 카테고리가 0개면 항목 추가가 막히므로 최소 하나는 필요하고, 이름은 관리 시트에서 바로 바꿀 수 있다.

기본 설정 시드는 `{ id: "singleton", goalPct: 80 }`.

## 5. 배포 순서

DDL과 배포 순서를 틀리면 데이터가 조용히 사라진다.

1. **0027 (A) 생성만 적용** — 새 테이블 3개. 구버전 코드는 이 테이블을 모르므로 아무 영향 없다.
2. **코드 배포** — 캘린더 읽기·쓰기 전부 제거 + 데일리 투두. 이 시점에 `loadAll`은 `family_events`/`event_categories`를 더 이상 조회하지 않는다.
3. **실동작 확인 후 0027 (B) 제거 실행** — `drop table family_events, event_categories`.

**실패 모드는 크래시가 아니다 — 이게 함정이다.** supabase-js v2의 `.select()`는 PostgREST 에러에 reject하지 않고 `{ data: null, error }`를 돌려준다. 그래서 순서를 어겨도 `loadAll`의 `Promise.all`은 멀쩡히 완주하고, `?? []`가 빈 배열을 만들어 **화면은 정상으로 보이는데 쓰기만 전부 사라진다**. 눈에 띄는 고장이 없으니 며칠을 모르고 쓸 수 있다.

- (A)를 건너뛰고 배포하면: 카테고리 0행 → 시드 insert도 실패 → 화면엔 `일상`이 멀쩡히 뜨는데 체크가 하나도 저장되지 않는다.
- (B)를 먼저 실행하면: 구버전 코드의 캘린더가 빈 채로 뜬다(앱은 살아 있다).

그래서 `loadAll`은 세 `daily_todo*` select의 `.error`를 `console.error`로 남기고 그 엔티티의 시드 insert를 건너뛴다 — "0행"과 "테이블 없음"을 구분하기 위해서다(`budget_versions`가 쓰는 방식과 같다). 이건 진단이지 마이그레이션의 대체가 아니다.

DDL 두 조각 모두 재헌님이 직접 실행한다. (B)는 복구 불가이므로 실행 전 `family_events` 전량을 JSON으로 백업해 둔다. (B) 실행 전 두 폰의 PWA를 완전히 종료했다 재실행한다 — 서비스워커는 없지만 실행 중인 인스턴스가 구 번들을 메모리에 붙들고 있다.

## 6. 계산 — `lib/dailyTodo.ts`

전부 순수함수. 컴포넌트는 계산하지 않는다.

```ts
// 그 날짜에 활성인 항목
activeOn(todos: DailyTodo[], iso: string): DailyTodo[]

// 판정식 (단일 경로)
//   onceDate ? iso === onceDate
//            : iso >= startDate && (endDate === null || iso < endDate)

// 그 날짜 진행률
progressOn(todos, iso): { done: number; total: number; pct: number }
//   total === 0 이면 pct = 0

// 카테고리별 묶음 (카테고리 sortOrder → 항목 sortOrder → title)
groupByCategory(todos, cats, iso): { cat: DailyTodoCategory; items: DailyTodo[]; done: number; total: number }[]

// 월 히트맵 — 각 날짜의 pct와 목표 달성 여부
monthProgress(todos, ym, goalPct): Map<iso, { pct; total; achieved; hasOnce }>

// 목표 달성 연속 일수. 오늘이 미달이면 어제부터 역산한다(오늘은 아직 진행 중이므로)
streak(todos, todayIso, goalPct): number
```

`monthProgress`는 날짜별로 `progressOn`을 호출해 만든다. 별도 계산식을 두면 히트맵과 상단 링이 다른 숫자를 말하게 된다.

## 7. 화면 — `components/dailytodo/`

```
DailyTodoApp.tsx      날짜 상태 보유, 아래를 조립
DateStrip.tsx         ‹ 8월 18일 (화) › + [오늘로]
MissionCard.tsx       원형 진행률 + 목표 달성 + 스트릭
TodoSections.tsx      카테고리별 섹션 + 체크 행
Heatmap.tsx           월간 달성 히트맵
manage.tsx            항목 폼 / 항목 관리 시트 / 카테고리 관리 시트
```

위→아래 순서:

1. **날짜 줄** — `‹ 8월 18일 (화) ›`. 오늘이 아니면 `오늘로` 버튼. 미래 날짜로도 이동 가능(예약된 1회성 확인용)
2. **미션 카드** — 원형 진행률 `3/8 · 38%`, 목표(80%) 달성 여부, `연속 N일`. 활성 항목이 0개인 날은 % 대신 `항목 없음`
3. **카테고리 섹션** — 색 점 + 이름 + `2/3`, 아래 원형 체크 항목 행. 1회성 항목은 제목 옆에 `1회` 표시
4. **히트맵** — **선택한 날짜가 속한 달**의 그리드. 셀 배경 농도 = 그날 달성률, 목표 넘긴 날은 도장(ring), 오늘은 별도 ring. 미래 셀에 1회성 예정이 있으면 점 하나. 셀 탭 → 그 날짜로 이동. 날짜 줄의 `‹ ›`로 달을 넘어가면 히트맵도 따라 바뀐다
5. **`+ 항목 추가`** / 헤더 우측 `관리`

**체크 규칙**
- 과거·오늘: 체크 가능 (어제 깜빡한 것 반영)
- 미래: 체크 비활성(회색). 아직 오지 않은 날이다
- 토글은 `doneDates`에 iso를 넣고 빼는 것. 같은 날짜가 두 번 들어가지 않는다

**항목 추가 폼**
- 제목, 카테고리 드롭다운
- `[매일] [특정일]` 토글. 특정일 선택 시 날짜 피커(기본값 = 현재 보고 있는 날짜)
- 매일: `startDate = 오늘`, `onceDate = null`
- 특정일: `onceDate = 고른 날짜`, `startDate`도 같은 값(정렬·백업용)

**삭제**
- 매일 항목: `endDate = 오늘`. 버튼 라벨은 `그만하기`. 과거 기록은 남는다는 안내 한 줄
- 1회성 항목: 그냥 지운다(레코드 삭제). 과거 기록이 곧 그 항목 자체라 애매함이 없다
- 둘 다 2단계 확인 (기존 `DeleteButton` 패턴)

**카테고리 관리** — `CategoryManager` 구조를 그대로 옮긴다. 이름·색(팔레트 스와치)·추가·삭제. 삭제 시 그 카테고리 항목은 첫 다른 카테고리로 재배정, 마지막 하나는 삭제 불가.

UI 부품은 `components/budget/ui.tsx`의 `Card`·`Sheet`·`Field`·`PrimaryButton`·`Pill`을 재사용한다.

## 9. 테스트 — `lib/dailyTodo.test.ts`

형식이 아니라 목적을 단언한다.

1. 오늘 항목을 추가해도 **어제 진행률이 변하지 않는다**
2. 항목을 그만둬도(`endDate = 오늘`) **어제 목록과 진행률은 그대로다**
3. 1회성 항목은 **지정일에만** 분모에 들어간다. 전날·다음날 분모에 없다
4. 같은 날짜를 두 번 체크해도 `doneDates`에 **한 번만** 들어간다
5. 스트릭은 목표 미달일에서 끊긴다. 오늘이 아직 미달이면 어제까지를 센다
6. 활성 항목이 0개인 날은 `pct = 0`, `achieved = false`
7. `monthProgress`의 각 날짜 pct는 같은 날짜 `progressOn`의 pct와 **같다** (히트맵과 상단 링이 갈라지지 않는다)
8. 카테고리 정렬은 `sortOrder` → 항목 `sortOrder` → `title` 순으로 안정적이다

기존 `lib/calendar.test.ts` 19건은 대상 코드와 함께 삭제된다. 나머지 테스트는 전부 통과해야 한다.

## 10. 가정

- 기본 카테고리 시드는 `일상` 1개. 실제로 쓰는 이름은 재헌님이 관리 시트에서 정한다
- 기본 목표는 80%
- 1회성 항목의 과거 지정도 허용한다 (지난주 일을 뒤늦게 기록하는 경우)
