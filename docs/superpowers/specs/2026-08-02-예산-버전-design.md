# 예산 「버전」 — 설계

- 작성 2026-08-02
- 설계 1/2(개념 합의) 2026-08-01 / 설계 2/2(화면·마이그레이션) 2026-08-02

## 문제

매주 가족회의로 예산 기준선이 갱신된다. 그런데 지금 기본 예산(`budgets.year_month = null`)을 고치면 **과거 달까지 소급된다** — `budgetForCategory`가 그 달 오버라이드가 없으면 무조건 현재 기본값을 돌려주기 때문이다. 8월 기준선을 반영하는 순간 연간 탭의 1~7월 소진률과 이미 발행한 7월 리뷰 리포트가 전부 새 기준으로 다시 계산된다.

**7월은 7월 당시 예산 그대로 나와야 한다.**

## 해법 — 버전 세트 + 시작월

예산을 **버전**으로 묶고, 버전이 **시작월**을 갖는다. 어떤 달의 예산은 "시작월이 그 달 이하인 버전 중 가장 늦은 것"이다.

```
v1  2026-06부터   ← 첫 기준
v2  2026-08부터   ← 8월 가족회의 결과
v3  2026-09부터
```

2026-07 조회 → v1. 2026-08·2026-09 조회 → v2, v3. 새 기준선을 만들어도 **과거 달은 건드리지 않는다.**

### 버린 것 — 「이번 달만 조정」

단발 오버라이드(`budgets.year_month = "YYYY-MM"`) 개념을 폐지한다.

- 근거 ①: **DB 실사용 0건**(2026-08-01 확인 — 예산 22행 전부 기본, 오버라이드 0).
- 근거 ②: 예산 소실 사고 2회(2026-07-03, 2026-07-26)가 모두 그 섹션의 삭제 버튼 주변에서 났다.
- 일회성 조정 니즈는 "복제 → 시작월 지정"으로 흡수한다.

`year_month` **컬럼과 기존 값은 보존**한다(되돌릴 여지). `Budget.yearMonth`는 죽은 필드가 된다.

### 덤 — 계정과목 신설·폐지가 자동으로 풀린다

v2 세트에 그 과목의 예산 행이 없으면 8월부터 예산 없음. 행별 `effective_from` 안(案)에서 어정쩡했던 부분이 별도 장치 없이 해결된다.

### 「월 → 버전 지정표」를 쓰지 않는 이유

설계 1/2에서는 `budget_months(year_month, version_id)` 테이블로 월에 버전을 붙이고 미지정 달은 직전 지정을 상속하는 안을 잡았다. 복제 버튼이 확정되면서 이 테이블이 과해졌다.

- 지배적 흐름은 "새 기준선 = 복제 후 수정"이고, 시작월 하나면 충분하다.
- 유일한 손해는 "10월만 v2로 되돌리기"에 내용이 같은 버전이 하나 더 생기는 것. 복제가 1탭이라 감수한다.
- 이득: 테이블 1개, 관리할 목록 1개. 버전과 적용 월을 따로 손보지 않아도 된다.

## 데이터 모델

```sql
budget_versions
  id           text primary key
  name         text not null          -- "v1", "8월 기준" 등 자유 입력
  start_month  text not null          -- "YYYY-MM"
  memo         text
  created_at   timestamptz default now()

budgets
  + version_id text references budget_versions(id)
```

- `budgets.id`는 **uuid 타입**이다(`categories.id`는 text). 복제 시 `crypto.randomUUID()`를 써야 하고, 슬러그를 넣으면 400 `22P02`가 난다.
- `budget_versions.id`는 text 슬러그(`bv-1`, `bv-<uuid>`).
- 금융 4테이블(`transactions`·`categories`·`budgets`·`recurring_expenses`)에는 `deleted_at`이 없다. `budget_versions`도 같은 계열이므로 **소프트 삭제를 두지 않는다**(하드 삭제 + 삭제 제약으로 보호).

### 적용 규칙

```
resolveVersion(versions, ym)
  = start_month <= ym 인 버전 중 start_month 최댓값
  ?? 가장 이른 버전            -- 폴백
```

폴백을 두는 이유: 가장 이른 시작월보다 앞선 달을 조회해도 예산이 비지 않게 한다. v1 시작월은 첫 거래월 `2026-06`이므로 폴백이 실제로 걸릴 일은 거의 없지만, 없으면 그 달만 소진률이 통째로 사라진다.

버전이 0개면 `null`을 돌려주고 모든 예산 조회가 `null`이 된다(현재 예산 미설정과 같은 화면).

## 계산 함수 — 인자 추가

설계 1/2의 "영향 범위 0"은 **틀렸다.** 버전 해석에는 버전 목록이 필요하고, `budgets` 배열만으로는 대신할 수 없다.

> v2에 식비 예산 행이 없으면 결과가 "예산 없음"이어야 하는데, `budgets`만 훑으면 v1의 식비 행을 잡아버린다. 계정과목 폐지가 자동으로 풀린다는 이 설계의 장점이 바로 여기서 나오므로 우회할 수 없다.

`lib/compute.ts`의 공개 함수에 `versions: BudgetVersion[]` 인자를 추가한다.

```ts
budgetForCategory(budgets, versions, ym, categoryId)
totalBudget(budgets, versions, ym)
categoryBudgetTotal(budgets, versions, categories, ym)
budgetBurndown(txns, categories, budgets, versions, ym)
groupBurnRows(...)               // budgetBurndown 경유
computeYearPnl(txns, categoryById, budgets, versions, categories, year)
```

파급은 전부 TS 컴파일러가 잡는 기계적 수정이고 로직 변경은 없다.

- 앱: `components/budget/Dashboard.tsx`·`Analysis.tsx`, 새 예산 탭, `components/pnl/YearPnl.tsx`
- 스킬: `skills/family-budget-review/assets/`

`budgetForCategory`의 `ym` 인자는 **버전 해석 전용**이 된다(오버라이드 조회는 사라진다).

## 화면

### 가계부 5번째 서브탭 「예산」

`대시보드 · 거래내역 · 지역화폐 · 고정지출 · **예산**` — 고정지출 오른쪽.

```
┌ 버전 ──────────────────────────────┐
│ v3  2026-09부터            [복제][수정] │
│ v2  2026-08부터  ·이번 달 적용중        │
│ v1  2026-06부터                        │
└────────────────────────────────────┘
┌ v2 과목별 예산            합계 3,884,781 ┐
│ 주거비 · 월세      540,000   [수정][삭제] │
│ 생활비 · 식비      700,000   [수정][삭제] │
└────────────────────────────────────┘
```

- 버전 목록은 **시작월 desc** 정렬. 이번 달에 적용되는 버전에 배지.
- 기본 선택 = 이번 달 적용 버전. 다른 버전을 누르면 아래 편집 영역이 그 버전으로 바뀐다.
- **복제** = 버전 행 + 그 버전의 예산 행 전체를 새 id로 복사. 이름·시작월을 물어 새 버전을 만든다. 이게 새 기준선을 만드는 표준 경로다.
- **수정** = 이름·시작월·메모.
- 예산 편집 영역은 현 `Plans.tsx`의 「계정 과목 예산 · 매달 적용」 섹션을 그대로 옮긴다(과목명·성격 Pill·사용/예산·진행바·합계). "매달 적용"이라는 말은 버전 체계에서 의미가 없어지므로 뺀다.
- 「전체 월예산(구버전)」 행 표시도 함께 옮긴다(삭제만 가능, 신규 생성 불가 — 현행 유지).

### 손익 「예산·목표」 → 「목표·관리」

## 안전장치

예산 소실 사고가 두 번 났다. 이번에는 잃는 단위가 "행"이 아니라 "버전 전체"라 더 크다.

- **이미 적용된 버전은 삭제 불가.** 시작월 ≤ 이번 달인 버전은 삭제 버튼을 비활성화한다(과거 달의 숫자가 통째로 바뀌는 것을 막는다). 미래 시작월 버전만 삭제 가능 + `window.confirm`.
- **마지막 1개 버전은 삭제 불가**(event_categories와 같은 패턴).
- **과거 버전 편집 경고** — 다음 버전이 이미 시작한 버전(= 더 늦은 시작월의 버전이 존재)을 열면 편집 영역 위에 배너: "지난 달 리포트 숫자가 바뀝니다" + `[이 버전 복제해서 수정]` 버튼. **차단은 하지 않는다**(오타 수정 같은 정당한 니즈가 있다).
- 예산 행 삭제의 `window.confirm`은 현행 유지.

## 마이그레이션 0025

가산적·idempotent.

1. `create table if not exists budget_versions` + RLS `family_all`
2. `alter table budgets add column if not exists version_id text references budget_versions(id)`
3. v1 시드 — `insert ... on conflict do nothing`, id `bv-1`, name **`v1`**(ASCII), start_month `2026-06`
4. 백필 — `update budgets set version_id = 'bv-1' where version_id is null`

이름을 ASCII로 두는 이유: 한글 문자열은 SQL INSERT로 넣지 않는다(0021에서 확립한 규칙 — 한글 시드는 `loadAll` 부트스트랩에서). 여기서는 시드가 1행이고 사용자가 앱에서 바로 이름을 바꿀 수 있어 ASCII INSERT로 충분하다.

### localStorage 모드 승격

저장소 이중화(`lib/repo.ts`)에서 로컬 모드는 원본 JSON을 그대로 읽으므로 마이그레이션이 닿지 않는다. `normalizeVaccine`·`normalizeFamilyEvent`·`normalizeTxn`과 같은 패턴으로, **버전이 하나도 없으면 v1을 만들고 `versionId` 없는 예산을 v1에 붙인다.** 클라우드·로컬 양쪽 경로가 같은 결과를 내야 한다.

🔴 **DDL을 배포보다 먼저 적용한다.** 0024 때 push가 DDL보다 먼저 나가 계정과목 저장이 조용히 실패하는 창이 열렸다.

DDL 적용은 개인 토큰(`~/.claude.json`의 `SUPABASE_ACCESS_TOKEN`, 중첩 위치)으로 Management API를 node https로 호출한다. auto classifier가 프로덕션 DDL에 **특정 마이그레이션 명명 승인**을 요구하므로 "0025 마이그레이션 적용해"처럼 지시받아야 통과한다.

작업 전 `db-backups/`에 전 테이블 스냅샷을 뜬다.

## 테스트

`lib/compute.test.ts`에 `resolveVersion` + 버전 반영 케이스를 추가한다.

- 시작월과 조회월이 정확히 일치
- 두 버전 사이의 달 → 앞 버전
- 가장 이른 시작월보다 앞선 달 → 폴백(가장 이른 버전)
- 버전 0개 → `null`
- **그 버전에 예산 행이 없는 과목 → `null`**(다른 버전 행을 잡지 않는다 — 이 설계의 핵심 보장)
